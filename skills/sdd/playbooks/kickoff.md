### Kickoff

**You own the map of the intent. The user decides.** Write no code. Do not mix facts and guesses. Throwaway probes outside the repository are allowed.

Send a request to write design documents to **Design docs**. Here, go only as far as closing the topics.

1. Listen first. Ask the first question (what the user wants, and why) before you write or map anything; the first reply asks this question only. If the user has not said anything yet, ask them to say what comes to mind. Read the input material if there is any. Record where it is by URL and commit; with no remote, by commit and repository-relative path. Save pasted material under `docs/input/`. An answer to the AI's question is a short step.
2. After the first answer, ask the setup questions one at a time; they are not topics. At a project kickoff, or a first kickoff on existing code, when the repository root already has `docs/` or holds other projects, ask which folder is the project root (`SKILL.md`). If the folder is not a Git repository, ask whether to run `git init`. If the project root has no rules file (`CLAUDE.md` in Claude Code, `.omp/AGENTS.md` in omp), show `references/project-rules.md` and ask whether to create it there; the harness starts from that folder. If only the other harness's rules file exists, see `SKILL.md`. Ask whether the harness folders (`.omp/skills/`, `.omp/agents/`, `.claude/skills/`, `.claude/agents/`) and `explanations/` are committed or excluded (`.git/info/exclude`); the rules file stays tracked. Create `docs/journal/` if it is missing; steps that ran before it existed write their entries then, each with its own date.
3. In someone else's repository, ask where the sdd documents live and whether they go upstream (the checker takes `--docs <dir>`). Read the CONTRIBUTING-style rules for commits, branches and sign-off. Run `git check-ignore` on the rules file; if it is ignored, ask. Never add a sign-off without asking.
4. On existing code, after the first answer, make a minimal map with `review/explain-full-map/SKILL.md`: the folder map, the data the work touches, the list of flows, at most 10 questions. Its sample flow is the flow the work touches. Vendored and generated folders get one row with a count, not a reading. Write a flow document (`review/explain-full-flow/SKILL.md`) only for a flow the work changes. Explanation documents live in the main checkout's `explanations/`, named `<kind>-<short hash>-<name>.html` (kind `map`, `flow` or `diff`). Do not regenerate one made at the same commit. Fix an error found later in place and note it in the header. Record each document as input material: committed documents name it by file name and commit; replies and the journal, by absolute path.
5. For a slice kickoff, propose the branch (`references/doc-templates.md`). Asking about the branch ends the step; write the brainstorming on the branch in the next step. The branch-question step's uncommitted entry moves to the new branch when it is created. Setup files written before the branch exists (the rules file, `docs/journal/` and the first steps), and a project kickoff's `00`, are committed on the default branch when the user asks, also on existing code; the slice branch is then created from that commit. A project kickoff and a slice kickoff asked for together run one after the other; the slice kickoff starts with the branch question. A worktree goes outside the project folder and needs the skill too (`SKILL.md`, Autonomy).
6. Write `docs/brainstorming/NN-<name>.md` and show it. NN is `00` for the project kickoff and the slice number for a slice kickoff. Existing code with no sdd documents gets slice kickoff `01`, with the purpose quoted from the README; the slice list starts in that document. It has three sections: what is settled, the list of topics to settle, and the AI's guesses. Mark each guess "unverified guess". Add the topics the user did not mention to the list.
7. Discuss the topics one at a time. Give options and a recommendation for each. A project kickoff closes only purpose, users, scope, out of scope and the slice list (a table, `references/doc-templates.md`), purpose first; feature topics go to the slice kickoff. A slice kickoff does not ask about the purpose again. When the user states a constraint, ask its reason once.
8. When a topic is settled, write the decision under "what is settled" and move to the next topic. Keep rejected options with a strikethrough. Do not delete them.
9. Reread the document from the top. Do the earlier decisions agree with the later ones? Does a guess have a counterexample? If a decision sentence hides a new topic, add it and go back to step 7.
10. Do the **Wrap-up** (`wrap-up.md`).

**Report:** the topics settled and their decisions, the topics left, the rejected options and why, the guesses that have a counterexample, what you took for granted.
